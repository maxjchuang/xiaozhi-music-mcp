# 飞书数据分析第二阶段方案

## 1. 背景与目标

第一阶段已经完成 MCP 侧音乐搜索事件、本地 SQLite 可靠队列、飞书登录授权、原始事件同步和首版仪表盘。截至本方案编写时，现有数据包含 108 条原始事件，主要覆盖搜索开始、搜索成功或失败，以及设备首次请求媒体代理。

当前数据仍无法回答以下关键问题：

- 用户真正听了多长时间；
- 哪些歌曲自然播放完成，哪些很快被停止或切换；
- 停止是用户偏好、搜索结果不匹配，还是网络、解码等技术故障导致；
- 用户说了什么、何时使用、一次交互经历了哪些步骤；
- 不同固件版本的播放稳定性是否存在差异。

第二阶段的目标是补齐固件侧真实行为事件，生成会话和播放业务投影，并把“播放后多久停止、自然完播率、快速跳过率”提升为核心分析指标，用于判断歌曲接受度和搜索结果质量。

## 2. 设计原则

1. 音乐播放优先。遥测采集、网络上报和飞书同步不得阻塞音频下载、解码、播放或唤醒链路。
2. 事实与推断分离。原始事件只记录事实，完播、快速跳过和疑似搜索不满意由可重建的投影计算。
3. 真实播放口径。播放时长按实际输出到扬声器的音频帧累计，不使用工具调用时间、代理首请求时间或简单的墙上时间差代替。
4. 明确结束原因。用户主动行为、自然结束和技术故障必须分开统计。
5. 本地优先。事件先可靠写入 MCP 本地 SQLite，再异步同步到飞书；飞书异常不影响音乐服务。
6. 隐私默认保护。不上传原始音频，文本默认脱敏，设备 ID 在 MCP 侧单向哈希。

## 3. 总体链路

```text
EchoEar 固件
  ├─ 唤醒、聆听、ASR、助手回复
  └─ 播放开始、停止、完成、切歌、欠载和错误
               │
               │ 异步局域网遥测
               ▼
小智音乐 MCP 遥测入口
               │
               ▼
SQLite 原始事件 + 可靠同步队列
  ├─ 会话投影
  └─ 播放投影
               │
               ▼
飞书多维表格
  ├─ 原始事件
  ├─ 会话记录
  └─ 音乐播放记录
               │
               ▼
使用总览 / 音乐质量 / 设备稳定性仪表盘
```

固件不直接访问飞书。MCP 作为局域网遥测接收端、数据事实来源和飞书适配层。

## 4. 第二阶段事件范围

### 4.1 会话与语音事件

- `device_booted`
- `wake_detected`
- `listening_started`
- `listening_stopped`
- `user_utterance`
- `assistant_response`
- `network_error`

`wake_detected` 区分唤醒词和触摸。设备只能记录成功检测到的唤醒，无法观察用户说出唤醒词但未被识别的次数，因此系统只能统计成功唤醒次数和唤醒后进入 ASR 的转化率，不能声称得到真实唤醒识别率。

### 4.2 音乐播放事件

- `playback_requested`
- `playback_started`
- `playback_stopped`
- `playback_completed`
- `playback_failed`
- `song_switched`
- `audio_underrun`
- `decode_error`

`playback_started` 必须在第一段有效 PCM 真正开始输出时产生，而不是在工具调用成功、下载开始或代理收到请求时产生。播放结束事件携带最终实际播放时长、媒体时长、结束原因、欠载次数和欠载累计时间。

## 5. 核心播放指标

### 5.1 单次播放事实

每次实际播放形成一条独立记录，至少包含：

- 实际开始出声时间和结束时间；
- 实际播放音频时长 `audible_played_ms`；
- 媒体资源时长 `media_duration_ms`；
- 原歌曲完整时长 `song_duration_ms`；
- 播放内容类型 `full` 或 `preview`；
- 开始后多久发生首次终止动作；
- 结束原因；
- 是否发生暂停和恢复、累计暂停时长；
- 欠载次数和欠载累计时长；
- 搜索词、最终歌曲、歌手、Provider 和链路 ID；
- 停止后的下一步行为。

同时保留两个时间口径：

- `audible_played_ms`：真正输出的音频时长，用于计算播放比例；
- `elapsed_since_start_ms`：从开始出声到结束的墙上时间，用于分析用户多快采取停止或切歌动作。

### 5.2 计算公式

```text
播放比例 = audible_played_ms / media_duration_ms
完整歌曲自然完播率 = full 且 natural_completed 的次数 / full 有效播放开始次数
试听片段完播率 = preview 且 natural_completed 的次数 / preview 有效播放开始次数
主动停止率 = user_stopped 次数 / 有效播放开始次数
快速跳过率 = 达到快速跳过条件的次数 / 有效播放开始次数
```

试听片段自然结束只表示试听片段完播，不能计为整首歌曲完播。网络、解码、设备关机等异常退出不进入用户喜好分母，但单独进入稳定性指标。

### 5.3 结束原因

结束原因使用稳定枚举：

| 结束原因 | 含义 | 是否进入偏好判断 |
| --- | --- | --- |
| `natural_completed` | 下载、缓冲和解码正常结束 | 强正向 |
| `user_stopped` | 用户明确要求停止 | 负向 |
| `song_switched` | 用户要求播放另一首 | 负向，且可能表示搜索不满意 |
| `interaction_interrupted` | 唤醒或触摸后未恢复播放 | 单独观察，不直接视为负向 |
| `network_failed` | 网络或上游流中断 | 否 |
| `decode_failed` | 音频解码失败 | 否 |
| `device_shutdown` | 设备关机或重启 | 否 |
| `unknown` | 无法确认 | 否，进入数据质量指标 |

临时被语音交互覆盖但之后继续播放，只记录暂停和恢复，不结束当前播放记录。

### 5.4 快速跳过分层

默认分层如下，阈值必须可以配置并支持后续重算：

| 行为 | 默认解释 |
| --- | --- |
| 0～10 秒主动停止或切歌 | 极可能结果错误或明显不喜欢 |
| 10～30 秒主动停止或切歌 | 大概率不满意 |
| 播放不足 25% | 低接受度或匹配不佳 |
| 播放 25%～75% | 中途退出，原因不确定 |
| 播放超过 75% | 高接受度 |
| 自然播放完成 | 强正向信号 |
| 完播后短期内再次播放 | 极强正向信号 |

这些标签是分析信号而非事实结论。歌曲排行需要同时展示样本数，避免单次播放产生过强判断。

## 6. 搜索结果不满意推断

第二阶段增加派生指标 `suspected_search_dissatisfaction`。默认满足以下条件时标记：

```text
歌曲实际开始播放
→ 15 秒内主动停止或切歌
→ 60 秒内再次点歌或搜索
```

结合后续行为进一步分类：

- 相同搜索词换成另一首结果：优先判断为候选匹配错误；
- 相同歌曲换 Provider：优先判断为播放权限、音质或资源问题；
- ASR 文本被纠正后重新搜索：优先判断为语音识别或查询归一化问题；
- 换成完全不同的歌曲：更可能是用户改变主意，不直接归因于搜索质量。

系统只输出“疑似”标签和证据字段，不把行为推断表述为确定的喜欢或讨厌。

## 7. 业务投影与飞书表

### 7.1 会话记录

一轮交互一条记录：

- 会话 ID、设备 ID、固件版本；
- 开始和结束时间、唤醒方式；
- 用户原话、助手回复、对话轮数；
- 是否触发音乐、涉及的播放链路；
- 会话结果和错误。

### 7.2 音乐播放记录

一次实际播放一条记录：

- 链路 ID、会话 ID、设备 ID；
- 原始点歌文本、规范化搜索词；
- 歌曲、歌手、专辑、Provider；
- `full` 或 `preview`；
- 请求、开始和结束时间；
- 首播等待时间；
- 实际播放毫秒、媒体时长、原歌曲时长；
- 播放比例、停止发生秒数；
- 自然完播、快速跳过和结束原因；
- 暂停、恢复、切歌和重复播放信息；
- 欠载、网络和解码错误；
- 后续动作和疑似搜索不满意分类。

投影由原始事件确定性生成，使用 `session_id` 和 `trace_id` 幂等更新，并支持从全部事件重建。

## 8. 仪表盘规划

### 8.1 使用总览

- 日、周、月会话次数和点歌次数；
- 使用时段和对话轮数；
- 唤醒方式分布；
- 热门搜索词、歌曲和歌手。

### 8.2 音乐搜索与播放质量

- 点歌漏斗：请求、搜索成功、实际开始、自然完成；
- 完整歌曲自然完播率和试听片段完播率；
- 主动停止率和快速跳过率；
- 停止时间分布；
- 各歌曲平均播放比例、自然完播次数和样本数；
- 高接受度歌曲与高跳过歌曲排行；
- 搜索词、结果歌曲和疑似不满意排行；
- Provider 的完播率、试听率和异常率；
- 重复播放歌曲排行。

### 8.3 设备稳定性

- 首播等待时间趋势；
- 欠载次数和累计欠载时间；
- 网络、解码和未知退出分布；
- 按设备和固件版本对比异常率；
- 遥测队列积压和数据完整性。

## 9. 隐私与保留策略

- 不采集或上传原始音频；
- 用户和助手文本默认采用 `masked` 模式；
- 支持 `off`、`masked`、`full` 三档文本策略；
- 原始设备 ID 只在接收瞬间存在，入库前单向哈希；
- 建议原始事件保留 30 天，会话与播放汇总保留 180 天；
- 支持按设备、会话和时间范围查询与清理；
- 飞书同步失败时事件保留在本地，恢复后自动补传。

## 10. 验收标准

使用真实设备完成以下闭环：

1. 唤醒设备并点播一首完整歌曲；
2. 播放超过一段时间后主动停止；
3. 再次点歌并在 15 秒内切换到另一首；
4. 完整播放一首歌曲直到自然结束；
5. 播放一个 30 秒试听片段直到结束；
6. 在播放中发起一次语音交互并恢复音乐；
7. 人为制造一次网络中断；
8. 验证每次播放的实际时长、比例、结束原因和后续动作正确；
9. 验证完整歌曲完播与试听片段完播没有混合；
10. 验证网络错误不计入用户主动跳过；
11. 验证会话、播放投影可以从原始事件重建且不产生重复记录；
12. 验证飞书断网和恢复同步不影响音乐播放；
13. 通过串口和听感确认遥测任务没有引入音频卡顿或唤醒退化。

只有固件能够准确区分自然完成、主动停止、切歌和异常退出，并且飞书能够按歌曲计算停止时间分布、实际播放比例和自然完播率，第二阶段才算完成。
