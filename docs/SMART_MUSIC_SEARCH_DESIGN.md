# MCP 侧音乐搜索准确性优化设计

## 1. 背景与目标

当前搜索链路会按 Provider 顺序查找歌曲，并返回第一首可播放的结果。这会把“拿到音频 URL”误当成“找到用户想听的歌”，主要表现为：

- 儿童发音或 ASR 近音字导致标题识别错误，例如“世界真细小”被识别为“世界真是小”。
- 高相关候选只有 30 秒试听时，系统可能跳到完整但无关的歌曲。
- 用户指定原唱或歌手后，系统可能静默降级到翻唱。
- 搜索成功率无法衡量最终歌曲是否匹配。

目标是在不修改 EchoEar 固件的前提下，将搜索升级为“查询理解、多候选召回、相关性排序、权限验证、可解释决策”链路。

核心原则：

1. 高相关的 30 秒试听优先于无关的完整歌曲。
2. 明确找不到优先于播放错歌。
3. 指定歌手时不静默降级到其他歌手。
4. Navidrome 中的高相关本地歌曲保持最高优先级。
5. 成功播放响应保持现有设备协议兼容。

## 2. 目标链路

```text
ASR 原始文本
    -> 查询标准化与意图提取
    -> 人工别名与曲库候选感知纠错
    -> 多 Provider 候选元数据召回
    -> 标题、拼音、歌手、版本综合评分
    -> 高分候选播放权限解析
    -> 完整播放 / 30 秒试听 / 不可播分类
    -> 自动播放 / 请求确认 / 明确失败
    -> 本地日志与飞书事件
```

## 3. 查询标准化与纠错

新增确定性的 `MusicQueryNormalizer`，负责：

- 删除“播放、来一首、我想听”等口语。
- 清理书名号、标点、重复空格。
- 从显式格式中提取歌手。
- 识别“原唱、儿歌、翻唱、现场版、伴奏、DJ”等版本偏好。
- 保留原始文本以便追踪 ASR 问题。

新增可配置别名文件，例如：

```json
{
  "世界真是小": "世界真细小",
  "公交车的轮子转啊转": "公交车的轮子转呀转"
}
```

别名只在音乐搜索中生效，不执行全局单字替换。首轮召回后，还会使用标题编辑距离和拼音相似度识别曲库中真实存在的高置信标准标题，不凭空改写查询。

## 4. Provider 两阶段接口

将当前过早返回音频的接口拆成：

```python
search_candidates(query, limit=10) -> list[TrackCandidate]
resolve_candidate(candidate) -> Track
```

`TrackCandidate` 仅包含 Provider、歌曲 ID、标题、歌手、专辑、时长、封面、原始排名和查询变体。排序后只对前 3～5 个候选获取音频 URL、歌词和播放权限，减少延迟。

## 5. 候选评分

初始使用可解释规则：

| 条件 | 建议分值 |
|---|---:|
| 标题完全一致 | +50 |
| 标题高度相似 | +20～40 |
| 拼音高度相似 | +10～20 |
| 指定歌手一致 | +25 |
| 儿歌、原唱等版本一致 | +10 |
| Navidrome 本地来源 | +8 |
| 未要求但为 Cover/翻唱 | -10 |
| 未要求但为 DJ/Live/伴奏 | -15 |
| 串烧或异常长标题 | -20 |
| 显式歌手不符 | -40 |

播放权限独立分类为 `full`、`preview`、`unavailable`和 `truncated`，不用低相关完整歌曲覆盖高相关试听。

决策阈值默认为：

- `score >= 85`：自动播放。
- `65 <= score < 85`：返回 `needs_confirmation` 及候选。
- `score < 65`：明确返回未找到。

阈值和候选数量由环境变量配置，便于根据真实数据调整。

## 6. 30 秒试听与账号诊断

30 秒试听不再被过滤，而是设置 `is_preview=true` 并参与正常排序。当最终候选是网易云试听版时，服务再执行登录状态检查：

| 状态 | 诊断 | 提示 |
|---|---|---|
| 无账号 ID | 登录失效 | 提醒执行 `netease relogin` |
| 已登录，`fee=1` 且 `payed=0` | 完整权益不足 | 可能会员过期、需购买或版权受限 |
| 已登录但仍只有试听 | 版权或接口限制 | 建议换版本 |

登录状态短时缓存，不阻塞普通搜索。试听成功响应保持 `success=true`，并增加 `is_preview`、`preview_duration`、`access_status`、`notice`、`recommended_action` 和 `account_command`。

## 7. 查询变体、性能和缓存

只在首轮没有高分候选时尝试：别名结果、纯标题、从真实候选推导的标准标题。最多使用 3 个查询变体。

性能约束：

- 每个 Provider 最多召回 10～15 个元数据候选。
- 只解析排名最高的 3～5 个候选。
- 搜索结果可缓存约 5 分钟，网易云账号状态缓存 5～10 分钟。
- 搜索总预算为 6～8 秒；Navidrome 高分精确匹配允许提前返回。

## 8. 事件与可观测性

搜索事件增加：原始查询、标准化查询、纠错类型、查询变体、候选数、选中排名、匹配分、淘汰原因、播放权限、账号诊断和总耗时。

后续以“播放 15 秒内停止、60 秒内重新搜索相似标题、不是这首”作为准确性反馈，而不只统计技术成功率。

## 9. 分阶段实施

### P0：准确性收口

- 查询标准化和人工别名。
- 多候选召回和两阶段 Provider 接口。
- 标题、拼音、歌手、版本评分。
- 自动播放最低阈值。
- 30 秒试听保留和网易云账号诊断。
- 搜索诊断日志、事件字段和真实案例回归测试。

### P1：交互优化

- 中置信度候选确认。
- 原唱不可用时询问是否接受翻唱。
- “不是这首”、“换原唱”、“换儿童版”等短期候选上下文。

### P2：持续学习与曲库建设

- 从飞书数据识别高频 ASR 错词，人工审核后写入别名表。
- 将高频但网易云无完整权益的歌曲补充到 Navidrome。
- 根据快速换歌率和纠错结果调整阈值。

## 10. P0 验收标准

1. “世界真细小”被识别为“世界真是小”时能够纠正。
2. 黄霍版 30 秒试听不再被过滤，且优先于无关完整歌曲。
3. 不再把《早点早点》当成《世界真细小》。
4. 指定宋冬野时不静默播放其他歌手版本。
5. “刺界”没有高相关候选时不播放无关歌曲。
6. 登录失效与会员权益不足能够区分；重新登录后重新验证。
7. Navidrome 精确匹配仍保持最高优先级。
8. 现有固件播放响应保持兼容，搜索 P95 时间不超过约 8 秒。
9. 纠错、候选评分和淘汰原因可从本地日志与飞书事件追踪。
